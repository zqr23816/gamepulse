# GamePulse 简历与面试讲解

## 30 秒项目介绍

GamePulse 是我为多人游戏场景设计的遥测与排行榜后端。客户端可批量上报游戏事件，FastAPI 服务通过 Pydantic 做数据校验，并使用 API Key 和幂等键控制访问与重复请求；SQLite 事务保证事件和幂等结果一致落库。匹配结果会通过独立的 Elo 领域服务更新排名，同时提供可部署的实时运营仪表盘、Docker 和 CI。

## 简历可用表述

- 使用 Python、FastAPI、Pydantic 与 SQLite 实现游戏遥测服务，设计批量事件摄取、排行榜查询、健康检查等 REST API，并自动生成 OpenAPI 文档。
- 基于 `Idempotency-Key` 与数据库写事务实现可重试事件上报，避免网络重传导致重复数据；将 Elo 算法提取为纯领域逻辑并完成单元/接口测试。
- 构建 React 数据运营仪表盘与 Cloudflare D1 在线演示，配置 Docker、GitHub Actions，实现前后端构建和测试自动化。

不要写“支持百万 QPS”“生产级高可用”等未经压测或真实生产验证的结论。

## HR 最关心的五个问题

1. **这是你自己做的吗？** 说明需求拆解、API 契约、事务模型、测试和部署均由你实现；第三方框架只承担基础能力。
2. **项目解决什么问题？** 游戏客户端网络不稳定，上报可能重试；运营又需要及时看到玩家、比赛和排行榜，因此核心矛盾是“可靠写入 + 快速查询”。
3. **最难的地方是什么？** 幂等不能只在内存中判断，检查与写入必须处于同一事务，否则并发重试仍可能重复落库。
4. **你做过什么取舍？** 演示采用 SQLite/D1 降低部署成本；清楚说明它的单写限制和 Kafka + ClickHouse/PostgreSQL 的演进路径。
5. **怎么证明质量？** 展示四个自动化测试、CI、构建结果，以及用相同幂等键请求两次时 `replayed` 从 `false` 变为 `true` 的证据。

## 技术面高频追问

### 为什么需要幂等？

客户端在超时后不知道服务端是否已成功处理，只能重试。GamePulse 把幂等键、响应结果和事件放在同一事务中：第一次写入后缓存响应；后续请求直接返回原结果，不再写事件。

### 现在的实现有什么并发风险？

SQLite 是单写者模型。`BEGIN IMMEDIATE` 能让竞争写入提前串行化，适合简历演示和中小流量，但高并发会产生锁等待。生产环境应使用具备更强并发写能力的数据库或消息队列，并为幂等记录设置过期策略。

### 排行榜为什么不是每次现算？

当前评分在比赛事务中增量更新，查询只做索引排序，是一种物化投影。规模扩大后，可把比赛事件写入流，异步消费者更新 Redis sorted set，并通过周期性快照校正。

### 如果事件量增长 1000 倍怎么办？

按四层拆分：网关限流与鉴权；Kafka 按玩家或游戏分区；消费者校验后批量写 ClickHouse；PostgreSQL 保存强一致业务状态，Redis 服务排行榜热读。增加死信队列、消费延迟指标和可回放事件日志。

### 如何测试幂等？

接口测试使用同一 `Idempotency-Key` 连续提交相同批次，断言第二次返回 `replayed=true` 且事件 ID 完全一致。进一步可增加多线程竞争测试和故障注入，验证事务提交前后重试行为。
